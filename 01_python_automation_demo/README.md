# Демо: автоматическая обработка заявок на закупку (Python, dry-run)

**Это учебная демо-работа**, сделанная для портфолио на выдуманных данных. Это не коммерческий проект и не внедрение у реального заказчика.

## Какую проблему показывает демо
В компании заявки на закупку приходят в таблице. Кто-то вручную проверяет, что заполнено всё нужное, ищет дубли, решает, что можно купить сразу, а что нужно согласовать, и рассылает письма. Демо делает эти шаги автоматически за секунды.

## Что делает скрипт `process_requests.py`
1. Читает заявки из CSV (так же выглядит выгрузка из Google-таблицы или Excel).
2. Проверяет каждую заявку: все ли поля заполнены, корректен ли e-mail, формат даты `ГГГГ-ММ-ДД`, количество (целое > 0), цена (> 0).
3. Присваивает статус:
   - `ОТКЛОНЕНА`: в данных есть ошибки (причина записывается);
   - `ДУБЛЬ`: такая же заявка (отдел, автор, позиция, количество) уже была выше;
   - `АВТООДОБРЕНА`: сумма не больше порога (по умолчанию 500 BYN, условное значение);
   - `НА_СОГЛАСОВАНИЕ`: сумма больше порога, нужен руководитель.
4. Печатает сводку (количество по статусам, суммы, срочные заявки на согласовании).
5. Записывает 4 файла в папку `out/`: `approved.csv`, `needs_approval.csv`, `duplicates.csv`, `rejected.csv`.
6. **Режим dry-run:** уведомления только печатаются (`[DRY-RUN] ...`). В коде нет отправки писем и сообщений вообще, адреса `@example.com` выдуманные.

## Схема процесса
```
CSV / таблица заявок
        |
        v
  чтение строк
        |
        v
  проверка полей ----- ошибка ----> ОТКЛОНЕНА --> уведомление автору
        |
        v
  проверка на дубль --- да -------> ДУБЛЬ
        |
        v
  сумма = кол-во x цена
        |
   <= порога ---> АВТООДОБРЕНА
   >  порога ---> НА_СОГЛАСОВАНИЕ --> уведомление руководителю
        |
        v
  сводка + файлы out/*.csv + уведомление команде
```

## Как запустить
Нужен только Python 3.8 или новее, ничего устанавливать не надо.
```
python3 process_requests.py sample_requests.csv
python3 process_requests.py sample_requests.csv --threshold 1000 --out result
python3 -m unittest -v        # 7 автотестов проверки правил
```

## Как то же самое собирается в n8n или Make (схема шагов)
Это описание схемы, а не готовый экспортированный сценарий: в n8n и Make я этот сценарий пока не собирал и не запускал. Логика та же, что в скрипте.

**n8n:**
1. `Schedule Trigger` (например, каждое утро в 9:00) или `Google Sheets Trigger` (новая строка).
2. `Google Sheets` (Get Rows): читаем заявки со статусом «новая».
3. `Code` (JavaScript или Python) или `IF`/`Switch`: проверка полей и e-mail, расчёт суммы, поиск дублей.
4. `Switch` по результату: ошибка / дубль / сумма <= порога / сумма > порога.
5. `Google Sheets` (Update Row): записать статус и причину в таблицу.
6. `Gmail`/`Email` или `Telegram`: письмо автору при ошибке, сообщение руководителю при согласовании. На время тестов узел отключают или шлют на тестовый адрес (аналог dry-run).
7. `Aggregate` + `Email`: итоговая сводка команде.

**Make:** то же самое модулями: `Google Sheets: Watch Rows` -> `Router` с фильтрами по условиям (ошибка, дубль, сумма) -> `Google Sheets: Update a Row` -> `Gmail: Send an Email` / `Telegram Bot: Send a Message` -> `Array Aggregator` -> итоговое письмо.

## Чего нет и что можно доработать
- Чтение напрямую из Google Sheets по API не сделано, скрипт читает CSV (из таблицы делается выгрузкой «Файл -> Скачать -> CSV»).
- Реальная отправка уведомлений не реализована специально.
- Порог и правила условные, под реальный процесс их настраивают вместе с заказчиком.
